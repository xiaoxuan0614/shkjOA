## 一、`stock_apply`（出入库申请）需扩展字段

| 字段 | 类型 | 说明 | 取值/示例 |
| --- | --- | --- | --- |
| `bizType` | string | 业务类型（区分领料/还料/采购） | `PICK` 领料 / `RETURN` 还料 / `PURCHASE` 采购 |
| `projectNo` | string | 关联项目分期编号（领料/还料/采购按项目） | 如 `XM100001` |
| `projectName` | string | 项目名称（分期名称） | 如 `一期工程` |
| `returnUser` | string | 还料人（还料申请用） | 如 `张小刀` |
| `supplierName` | string | 供应商（采购已改独立采购订单模块，此字段保留备用） | 如 `某某供应商` |
| `expressNo` | string | 快递单号（采购到货，采购改独立模块后可不用） | 如 `SF123` |
| `executeStatus` | string | 执行状态（区别于审批状态 `status`） | 领料/还料：`待出库`/`已出库`、`待入库`/`已入库`；采购：`待采购`/`采购中`/`已到货`/`已入库`；另有 `已挂起` |

> 前端提交时还会带 `applyUserId`（申请人ID）、`deptId`（部门ID）、`deptName`（部门名称）——这三个接口文档 `StockApply` 已原生支持。

### 明细 `StockApplyItem` 需扩展字段（明细维度出库/入库用）

| 字段 | 类型 | 说明 | 用途 |
| --- | --- | --- | --- |
| `outQty` | number | 领料已出库数量（按所选单位累计） | 前端算出「剩余可出数 = 申请数量 − outQty」，防重复出库 |
| `inQty` | number | 还料/采购已入库数量（按所选单位累计） | 同上，剩余可入数 = 申请数量 − inQty |
| `shouldReturn` | number | 应还数量快照（还料申请提交时把 canReturn 存下） | 还料入库弹窗显示「应还/实际还/最终入」三层数量 |
| `actualReturn` | number | 实际还库数量（还料申请时填的 returnQty） | 还料三层数量之一 |
| `specRemark` | string | 规格型号/差异说明（采购入库实际规格变化等） | 差异留痕（也可写台账 remark） |

> 还料三层数量关系：**应还数量 shouldReturn → 实际还库数量 actualReturn → 最终入库数 inQty**（库管入库时确认，不一致逐条写说明）。

## 三、接口参数约定（前端已按此调用）

| 接口 | 传参方式 | 说明 |
| --- | --- | --- |
| `POST /stock/apply/cancel` | **query** `id` | 撤回/取消申请（撤回后 `status` 置为 `已撤回`） |
| `POST /stock/apply/delete` | **query** `id` | 删除申请 |
| `POST /stock/apply/deleteBatch` | query `ids` | 批量删除 |
| `POST /stock/apply/approve` | body `StockApplyApproval` | 审批通过（`applyId`+`approvalResult=AGREE`+`approvalComment`+`items?`） |
| `POST /stock/apply/reject` | body `StockApplyApproval` | 驳回（`applyId`+`approvalResult=REJECT`+`approvalComment`+`items?`） |
| `POST /stock/apply/edit` | body `StockApply`（含 `id`） | 撤回/驳回后重新提交：前端把状态改回 **`PENDING`**（字典英文码，此前误传中文「待审批」已修正）、`executeStatus` 改回待出库/待入库后提交 |
| `GET /stock/apply/list` | query | 建议支持按 `bizType`、`status`、`applyUserId`、`applyType` 过滤（前端采购/我的申请/状态筛选会用） |

> **`items` 明细审批结果（审批拆解，2026-08-14；apifox 已确认，无需后端改造）**：`approve/reject` 入参 `StockApplyApproval` 支持 `items:[{itemId, approve, unitQty?, remark?}]`。`items[].approve` 三态：**`true` 通过 / `false` 驳回 / `null` 暂不处理**（null 可不提交该项）。整单审批不带 `items`；**明细逐条 / 混合审批**把结果经 `items` 提交，后端按 `itemId` 逐条落 `StockApplyItem` 审批结果，并刷新整单 `status`（全通过→`APPROVED`、全驳回→`REJECTED`、部分→`PARTIAL_APPROVED`）。前端明细当前审批状态**从 `queryById` 返回的 `approvalList` 按 `itemId` 取最新一条推算**（不靠 `itemList[].status`）：`approvalList` 每条含 `itemId`、`approvalResult`(AGREE/REJECT)、`items:[{itemId, approve}]`，匹配顺序为顶层 `itemId` → `items[].itemId`。

> **出入库申请执行入参（2026-08-14 第八轮）：单条 + 批量统一走 `POST /stock/apply/execute`**，不再逐条调 `manualIn/manualOut`：
> - Body `StockApplyExecuteRequest = { applyId, itemIds?, items? }`，`items:[{ itemId, executeQty }]`（`executeQty` 空=执行剩余数量，`items` 空=按 `itemIds` 或全部待执行明细）；**方向由申请自身决定**，无需传 `ioType`。
> - **无 `approvalUserId` 字段**：执行人由**后端从登录 token 取**，需后端落台账记录执行人（`approvalUserId`/`createBy` 均可），之后按该 id 查询执行记录。
> - **无 `remark` 字段**：弹窗「说明(留痕)」列暂不提交（本地保留），**待后端给 `StockApplyExecuteItem` 补 `remark`** 后再随 execute 提交。
> - **⚠️ 实测（2026-08-14）：execute 已能按明细拒绝已执行完成的项**（返回「执行失败：所选明细已执行完成：XXX」），但前端拿不到已执行数量——`queryById` 不返回 `StockApplyItem.outQty/inQty`，且执行台账 `ioRecord` 无 `sourceId=申请id` 的行（sourceId 可能是明细 id 或未写），前端只能按台账聚合兜底算「剩余可执行」，与后端实际执行状态对不上，**会重复提交已执行项被后端拒绝**。请后端在 `queryById` 明细里返回 `outQty`(领料已出) / `inQty`(还料/采购已入)，前端即可精确算剩余，避免重复执行提示。
> - **✅ 明细分页接口 `GET /stock/apply/items` 已带执行信息**：明细含 `executedQty / executeStatus / executeUserId / executeUserName / executeTime`，独立详情页「物料明细 tab」已按此展示执行状态/执行人/执行时间；列表「剩余可执行」仍按台账聚合兜底，待 `queryById` 补 `outQty/inQty` 后精确化。

> **`manualIn` / `manualOut` 执行入参（2026-08-14 修正，仍用于采购入库 `StockInModal.vue` 与库存管理页手动出入库 `IOModal.vue`）**：
> - **无 `model` 字段**：接口入参不含规格型号，前端不再传（此前误传 `model` 已移除）。
> - **`unitId` 从字典 `inv_unit` 取**：申请页提交明细只带 `unitName`（单位来自物料 `unitList` 子表，后端明细回传的 `unitId` 不可靠）→ 前端执行出入库时按单位名从字典 `inv_unit` 反查 value（`material.util.ts` `resolveDictUnitId`），匹配不到兜底明细 `unitId`。
> - **传执行人 `approvalUserId`**：执行出入库（执行弹窗 + 批量出入库）时传 `approvalUserId`（当前登录用户 id = `getCurrentUser().applyUserId`），**后端应落库记录执行人**（台账表 `approvalUserId`/`createBy` 均可），之后按该 id 查询执行记录。
> - `sourceType=apply`、`sourceId=申请/订单id`、`sourceNo=单号` 保持。

## 四、采购订单（`/project/purchaseOrder`，前端已改走独立模块）

- 接口文档已有：`/project/purchaseOrder/list|add|edit|delete|deleteBatch|queryById`；明细 `/project/purchaseOrderItem/*`。
- **`add` / `edit` 请求体需支持 `itemList`**：前端一次提交"订单头 + 明细"（主表字段 + `itemList:[{materialId, materialName, materialCategory, brand, model, unit, quantity, unitPrice, amount}]`）。若后端按主表+明细分开保存，请在 `add`/`edit` 里接收 `itemList` 并落 `purchase_order_item` 表（`orderId` 回填）。
- 前端采购状态流转：`待采购 → 采购中 → 已到货 → 已入库`，通过 `edit` 更新 `status` 字段实现。
- **待采购可修改**：`edit` 接收完整订单头 + `itemList`（编辑后仍为 `待采购`）。
- **未入库可关闭（填原因）**：`edit` 支持 `status=已关闭` + `closeReason`（关闭原因，前端必填）；`OaPurchaseOrder` 需补 `closeReason` 字段。状态字典 `purchase_order_status` 已含 **已关闭**（见 `docs/物料模块字典配置.md`）。
- 入库：前端逐条调 `/stock/ioRecord/manualIn`（`sourceType=apply`、`sourceId=订单id`）生成台账，再把订单 `status` 置为 `已入库`。
- 前端会调 `/project/supplier/list` 作供应商下拉（接口文档已有）。
