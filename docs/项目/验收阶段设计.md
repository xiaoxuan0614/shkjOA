# 验收与返工阶段设计

> 更新：2026-09-10。当前口径：全部工序完成后进入待验收，开始验收后进入验收中，无需手动提交；内部验收由运维部门经理办理，外部验收由本项目经理办理；两项都通过才进入质保，任一项不通过可进入单工序返工闭环。

## 一、状态流程

```text
IMPLEMENTING / REWORKING
  → 当前轮全部工序 COMPLETED
  → ACCEPTING（内部、外部两条验收并行，并生成待办）
      ├─ 两项都 PASSED → WARRANTY
      └─ 任一项 FAILED → 申请返工 → 返工审批
                            ├─ 驳回/撤回 → 修改后重提
                            └─ 通过 → REWORKING
                                      → 统一返工工序完成
                                      → ACCEPTING（自动复验，关联当前 reworkId）
```

项目主状态只表达当前阶段，内部/外部各自进度由验收记录的 `acceptStatus` 表达：`NOT_STARTED`、`IN_PROGRESS`、`COMPLETED`、`CANCELLED`。外部验收在接口中仍使用 `acceptType=CUSTOMER`。前端不显示手工“进入质保”；是否进入质保由后端在两项都 `PASSED` 后统一计算。

## 二、提交与办理验收

`POST /project/acceptance/submit` 已废弃，PC 不再调用。全部工序完成后自动进入验收是当前业务要求，由后端负责；工序接口文档尚有旧说明，不由前端额外调用状态接口补推。

内部与外部验收的资料查询/保存统一使用 `GET/POST /project/acceptance/list|edit`，通过 `acceptType=INTERNAL|CUSTOMER` 区分；不得再调用历史 `/project/internalAcceptance/*`。完成统一使用（开始由后端自动处理）：

- `POST /project/acceptance/complete`。

返工复验必须携带当前 `reworkId`。内部验收由运维部门经理办理并使用 `project:internalAccept`；外部验收由合同指定的本项目经理办理并使用 `project:accept`。两者上传的主验收文件统一保存到 `completionReportFileId`，外部验收可另存 `acceptanceFormFileId`。

项目详情“验收记录”显示两张并行卡片，不再允许任意选择办理负责人：内部卡片只对拥有内部验收权限的运维部门经理开放；外部卡片同时校验 `project:accept` 和当前用户是否为该项目经理。两张卡片都必须上传各自验收文件，失败时说明必填；不再展示实施完成日期，验收办理时可选择验收日期，保存资料使用 `acceptDate`，完成验收将所选日期按 `YYYY-MM-DD 00:00:00` 传入 `acceptEndDate`；日期必选。已完成记录及历史表只读显示 `acceptEndDate`，缺失显示“—”。

## 三、返工申请

当任一当前轮验收已完成且结果为 `FAILED` 时，拥有 `project:rework:apply` 的人员可从该失败记录发起返工。每张返工单固定包含：

- 来源失败验收 `sourceAcceptanceId`；
- 返工原因（必填）与说明；
- 一个统一返工工序 `process`；
- 可为空的本轮额外领料计划 `materials`。

统一工序必填：工序名称、现场负责人、计划开始日期、计划完成日期、预计工时；完成日期不得早于开始日期，预计工时不得小于 0。返工不是多工序列表，前端只编辑和提交一个 `process` 对象。

返工材料的 `plannedQty` 只表示本轮需要新增领取的数量。现场已有余料在同一分期共享，不在返工计划中重复申请。

## 四、返工审批与 version

返工审批状态使用统一 `approval_status`：`-1` 待提交、`0` 驳回、`1` 审核通过、`2` 待审批、`3` 已撤回。

关键接口：

- `GET /project/rework/list`；
- `GET /project/rework/queryById`；
- `POST /project/rework/add|edit|submit|withdraw|approve`；
- `GET /project/rework/materials`。

`version` 是返工单乐观锁，处理规则固定如下：

1. 编辑打开时通过详情接口读取最新 `version`，编辑请求传 `id + version`。
2. 提交、撤回、审批在真正调用动作接口前，再读取一次详情并使用刚返回的 `version`。
3. “保存并提交”先保存草稿，再读详情取得保存后的新 `version`，然后提交。
4. 任意过期 version 由后端拒绝；前端不能静默覆盖，也不能自动拿旧内容重试。
5. 每次成功动作后重新加载返工列表和项目状态。

审批通过后后端生成一条普通项目工序、固化本轮额外领料计划并把分期推进为 `REWORKING`。返工审批人权限为 `project:rework:approve`。

## 五、返工领料与执行

返工领料沿用普通领料页面和 `/stock/apply/add|edit`，固定传 `applyType=OUT`、`bizType=PICK`、`usageType=PROJECT`、`periodId`、`reworkId` 与最小化 `itemList`。

页面只从 `GET /project/rework/materials?reworkId=...` 读取本轮额度，并只展示 `availableApplyQty>0` 的物料，不混入首次计划物料。库存审批与实际出库仍沿用原出入库流程。

返工工序执行复用正常实施能力：工序开始、施工日志、打卡、实际用料和工序完成都按后端生成的 `processId` 处理。完成该唯一返工工序后，后端将返工执行状态置为 `COMPLETED`，分期回到 `PENDING_ACCEPT`。

## 六、页面与待办

- 项目列表/详情：`PENDING_ACCEPT` 显示“提交验收”；项目详情继续不显示“实施完成”。
- 项目详情“验收记录”：展示当前轮内部/外部验收、历次验收和返工管理入口。
- 进入 `ACCEPTING` 时后端同步创建 `PROJECT_INTERNAL_ACCEPTANCE` 和 `PROJECT_EXTERNAL_ACCEPTANCE` 两条待办；前者指派运维部门经理，后者指派项目的 `projectManagerUserId`。建议 `bizId=验收记录ID`、`bizSubId=periodId`，`actionParams` 至少包含 `periodId/acceptanceId/acceptType/reworkId`。
- 两类验收待办均跳转 `/project/detail/:periodId?tab=acceptance&acceptType=...`；相应验收完成或当前轮取消时后端关闭待办。
- 返工抽屉：草稿编辑、提交、撤回、审批、详情、额外领料入口都在一个抽屉内按权限显示。
- 首页返工待办：按 `todoType/actionKey/title` 识别后跳转 `/project/detail/:periodId?tab=acceptance&reworkId=...`。
- 返工管理不新增菜单或独立路由；所需按钮权限挂在项目管理节点下。
