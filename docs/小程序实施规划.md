## 二、核心业务逻辑（状态机 + 关键规则）

### 2.1 报修 → 维修工单 主流程（核心）

```
客户报修(BX) → 信息部门派单 → 运维接单(选线下预约/线上维修)
  → 线下：预约(YY单) → 签到 → 维修日志(1/2/3步) → 结束打卡 → 维修完成(WX单)
  → 线上：首次日志生成单号 → 完成
  → 需还料：先还料 → 库管核对入库 → 提交审核
  → 管理员审批(通过/驳回) → 待评价 → 客户核对信息+签字+评价 → 已完结/关闭
任意环节可：驳回 / 撤回(未开始) / 转单 / 关闭(填原因)
```

**状态枚举（原型）**：未开始/未处理/待接单/已派单/进行中/待确认/待审批/待评价/已完成/已撤回/已驳回/已关闭/还料中/转单待确认。

### 2.2 关键业务规则（原型标注，实现时必须遵守）

1. **还料数量 = 申请数量 − 使用数量**；还料信息按关联单号统计用料记录，只展示还料量>0 的物料。
2. **线下维修完成需先还料**，库管核对好数量入库后，才可提交审核。
3. 报修**没开始的可以撤回**；运维一旦接单，状态变"进行中"。
4. 客户确认（维修确认单）固定三步：**核对信息 → 签字确认 → 评价建议**。
5. 线下维修要**签到/结束打卡**（定位，位置异常填原因）；**软件线上维修不需要预约单**，首次填日志生成单号。
6. 巡检表：左侧巡检对象 + 右侧填写项；未完成显示红点，**切换菜单自动保存**；无红点才显示提交；办结按钮仅未办结显示；可下载巡检单。
7. **待办事项 8 类**：项目工序即将到期(2天)、工单提交审批、用还料申请、转单信息、内协邀请、报修提醒、报修超 2 小时未处理、巡检任务即将到期(3天)。
8. 车辆记录：时间/定位自动带出，填写人=驾驶员。
9. **负责人** = 客户线上报修谁接单 / 电话报修谁填预约单；预约单号未开始前可修改。

### 2.3 单号规则

| 前缀 | 含义 | 示例 |
| --- | --- | --- |
| BX | 报修单 | BX202510240934 |
| GZ | 故障单/工单 | GZ202510240934 |
| YY | 预约单 | YY20250914092201 |

### 5.2 小程序目录规划（对照设计）

```
src/service/            # 请求层 + 按域拆 API（repair/stock/project/implement/vehicle/inspection）
src/pages/customer/     # 客户角色：home / repair / repairRecord / confirmSign
src/pages/ops/          # 运维：home / accept / reservation / material / repair / vehicle / punch / implementLog / project / inspection
src/pages/stock/        # 库管：materialApply（出入库）
src/pages/admin/        # 管理员：approval
src/components/         # 复用模板通用组件 + 新增业务组件（时间线/状态卡片/签名板/图片视频上传/定位）
src/store/              # user（去租户）+ 新增角色/tab 状态
```

### 5.3 关键注意点

1. **签名必须复刻**：所有请求带 `X-TIMESTAMP` + `X-Sign`（MD5(参数升序 JSON + 密钥)），否则后端拒请求。工程已依赖 `md5`。
2. **字典/状态不硬编码**：所有下拉/标签走后端 `sys_dict`（封装 `dict.js` 拉取缓存）。
3. **编号不手填**：BX/GZ/YY/WX/SG/XM/XJ 由后端生成，前端只读展示。
4. **照片/视频**：`/sys/common/upload` 统一上传，报修/维修/打卡/巡检到处用。
5. **定位**：签到/打卡/车辆记录都要经纬度+地点，模板 `useGeoPosition` 现成。
6. **tabBar 按角色**：客户=首页/记录/我的；运维=首页/打卡/我的；库管/管理员单页入口即可。
