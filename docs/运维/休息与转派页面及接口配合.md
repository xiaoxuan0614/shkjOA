# 休息与转派：正式接口对接与优化清单

核对日期：2026-10-30。来源：刷新后的 Apifox 项目 8679942，已逐项读取下列9个接口的请求和响应；未发现这些接口使用外部 schema 引用。

**状态边界：接口文档已提供正式契约；双端已接入正式接口并移除本模块示例数据。文档存在不等于运行服务已部署、授权或启用。本文替换此前“接口名称待定”的草案，不修改现有维修转单审批。**

## 1. 已明确的业务规则

- 固定4名不同有效运维成员及顺序。休息按预计执行时段与休息区间 `[startAt,endAt)` 重叠判断，统一 Asia/Shanghai。
- 默认 AUTO，主管可逐单或批量指定 MANUAL，也可恢复 AUTO。手动指定不推进自动轮值游标；预览不消耗游标。
- 主管确认直接生效，不走审批。同一事务保存休息、转派、游标、历史和待办，任一失败整体回滚。
- 取消休息不会把已转派工单转回，也不会回退游标，只恢复后续自动派单资格。
- 需V166/V167迁移、权限授权及管理员显式初始化。初始化仅首次允许，启用后不能重置名单和游标。

### 与此前需求不同的两项行为（需业务确认，不应静默上线）

1. preview检查当前负责人所有未完成单，不按原分配来源过滤；此前讨论限定自动派单。页面正式接入应标“受影响的未完成维修单”，不能继续宣称仅自动派单；若仍要求原范围，须后端调整筛选。
2. 启用四人轮值后，新报修缺少预计执行时段先待调度，主管保存计划后才尝试自动派单。需要有待调度列表和计划入口，否则新增报修可能长期没有接收人。

## 2. 接口与页面位置

| 方法及接口 | 页面用途 | 关键约定 |
| --- | --- | --- |
| GET /repair/rest/options | 页面进入时读能力和四人名单 | canManage、canConfigure、pool、members、timezone |
| POST /repair/rotation/configure | 管理员首次初始化 | userIds严格4人且顺序固定、nextPosition=1..4、configVersion |
| GET /repair/rest/calendar | 按日期看排班与休息 | date必填；dutyUsers仅展示，不决定派单；rests最多100条，超出转list分页 |
| GET /repair/rest/list | 休息记录查询 | userId/from/to/status/pageNo/pageSize；最大100条每页 |
| GET /repair/rest/detail | 休息与转派历史 | id；rest及assignments历史姓名快照、dispatchMode和游标 |
| POST /repair/rest/preview | 计算受影响工单及完整分配预览 | 只读；返回items、canConfirm、blockedReasons、previewToken、expiresAt |
| POST /repair/rest/confirm | 确认休息并立即转派 | 完整工单集合、最后一次previewToken、requestId；响应每单EFFECTIVE |
| POST /repair/rest/cancel | 取消未结束的有效休息 | id、version、requestId、reason；ordersReturned恒false |
| POST /repair/order/schedule | 主管维护预计执行时段 | orderId、plannedStartAt、plannedEndAt、工单version、reason；返回WAIT_DISPATCH或ASSIGNED |

休息管理需要主管/管理员身份且具有 `repair:rest:manage`；初始化还需管理员身份与 `repair:rotation:configure`。PC原值班表编辑权限和移动端canManage只是旧预览入口依据，正式接入须统一以上后端能力，不能当作已具备正式写权限。

## 3. 双端一致的调用顺序

1. 读取options：无管理能力显示无权限；pool未启用时显示待初始化；普通主管不显示初始化操作。不可打开页面时自动初始化。
2. 用户选日期后读calendar；选人取四人members，不能继续用整个运维部或示例名单替代固定池。
3. 录入休息起止，带`+08:00`；允许跨日，结束须晚于开始和当前时间、跨度不超过366天。全天用当天00:00至次日00:00，避免旧预览23:59漏最后一分钟。
4. 首次preview可省略assignments，未指定项默认AUTO。展示服务器返回的每单mode、suggestedTargetName、预计执行时段和阻断原因，不自行计算接收人。
5. 候选使用**每单**eligibleCandidates，canAssign=false禁选并显示原因。批量指定必须对所选每单均可用；否则列出不可用单，不默默部分覆盖。
6. 逐单/批量指定或恢复AUTO后重新preview，携带完整当前选择；不能只改本地姓名继续沿用旧token。防抖及请求序号保护，过时响应不得覆盖新方案。修改人员或休息时段应清空旧方案。
7. canConfirm=true且token未过期才允许确认。检查通过后展示自动/指定数量和预计接收人，主管确认才调用confirm。没有受影响工单时也须preview后按服务器canConfirm决定是否允许仅登记休息。
8. confirm提交全部items对应的assignments：AUTO不传targetUserId；MANUAL传实际指定ID。使用同一预览的userId/startAt/endAt和previewToken，备注字段是remark，非reason。
9. 成功展示服务器最终接收人和休息记录，刷新calendar/list与待办；不在请求返回前显示“已转派”。详情用detail，取消需确认原因并带最新rest.version。

## 4. 请求示例（按当前契约）

初次预览：

```json
{
  "userId": "rest-user-id",
  "startAt": "2026-11-01T08:00:00+08:00",
  "endAt": "2026-11-01T12:00:00+08:00"
}
```

调整后重新预览时加入以下assignments；拿到新token再确认：

```json
{
  "userId": "rest-user-id",
  "startAt": "2026-11-01T08:00:00+08:00",
  "endAt": "2026-11-01T12:00:00+08:00",
  "assignments": [
    { "orderId": "order-1", "mode": "AUTO" },
    { "orderId": "order-2", "mode": "MANUAL", "targetUserId": "target-user-id" }
  ],
  "requestId": "unique-request-id",
  "previewToken": "token-from-latest-preview",
  "remark": "调休"
}
```

上例是confirm请求；再次preview仅使用userId、startAt、endAt、assignments。旧草案的previewId不是当前字段。

## 5. 阻断、冲突与重试

| 服务端原因 | 双端应显示/执行 |
| --- | --- |
| REST_OVERLAP | 与已有休息重叠，调整时段 |
| MISSING_SCHEDULE | 缺少预计执行计划，先补计划，再预览 |
| WORK_IN_PROGRESS | 已开始执行，主管另行处理 |
| APPROVAL_IN_PROGRESS | 存在待审批申请，处理后重查 |
| NO_ELIGIBLE_RECEIVER | 无可接人员，不能派给休息人员 |
| CANDIDATE_UNAVAILABLE | 指定人员不可用，更换或恢复自动后重查 |
| ORDER_SET_CHANGED | 工单集合已变化，重新预览并核对新增/移除项 |
| PREVIEW_CHANGED / PREVIEW_EXPIRED | 方案变化或10分钟token过期，重新预览并再次确认 |
| REQUEST_REUSED | 同幂等号用了不同请求体；不能换号盲目再次提交 |

HTTP 200不代表业务成功，以success判断。网络超时/断网结果不确定时冻结原提交内容与requestId，只能同号同内容重试或核对详情，防止二次登记/推进游标。明确返回预览失效且确认未落库后，重新预览形成新方案，使用新的请求号；不能把旧requestId配上新token重试。

## 6. 仍建议后端完善的文档项

以下为核对发现的缺口，不作为已支持能力：

1. **错误码响应位置**：顶层code定义为integer，但文案给出ORDER_SET_CHANGED等字符串。请给出稳定的errorCode字段或数字映射及失败JSON；前端不能解析中文message判断业务分支。
2. **列表展示信息**：preview.items目前只有工单号、负责人ID、计划等，没有客户/项目/故障摘要；请补可见范围内的摘要或明确从哪个接口批量获取，避免双端逐单查询详情。rest/list缺休息人姓名和创建人/创建时间；优先补快照，避免历史账号变化造成错名。
3. **初始化候选**：options未初始化时members为空，未提供可选运维成员列表。请明确管理员获取候选的正式接口及权限；不要依赖普通主管可读系统用户管理接口。
4. **班次枚举和空值**：calendar.dutyUsers.shiftType未解释数值含义；schedule、suggestedTargetUserId、blockedReason等描述可null，schema却只声明object/string。请补枚举、required及nullable，使类型生成和空态处理一致。
5. **options无权限行为**：接口描述要求已有管理权限，同时返回canManage。请明确未授权是业务拒绝还是success=true/canManage=false，以及已授权但未初始化的准确响应示例。
6. **计划与范围细节**：明确缺失计划工单为何纳入某个休息时段的阻断集合、已结束审批与哪些待审批类型影响APPROVAL_IN_PROGRESS、空工单集合的确认行为。
7. **确认/取消并发与返回**：给出冲突错误JSON、cancel版本冲突码、preview受影响单数量上限，以及无可分配人员时待调度记录的查询入口。不要只在描述中给出行为。
8. **名单后续维护**：当前启用后永久禁止重置；人员离职/停用如何更换需另定管理员迁移策略，不应让前端直接重置四人池或游标。

## 8. 正式接入（2026-10-30，覆盖此前预览说明）

PC维修列表增加休息与转派、待调度/执行计划入口，值班表保留休息入口；移动端维修列表提供同样入口。均以options.canManage展示，不再依据旧预览权限。本次未修改菜单授权、未初始化固定池。

双端支持默认AUTO、逐单/批量MANUAL、恢复自动、重新预览、明确确认、休息历史与取消。候选和分配结果以服务端为准。确认/取消结果不确定时锁定原请求，只允许同号同内容重试。计划编辑重新读取工单version；提交不确定先核对工单。

order/list尚未声明dispatchStatus筛选及schedule摘要，兼容方式为scope=ALL、workStatus=PENDING每页10条，最多3并发读取详情识别WAIT_DISPATCH/ASSIGNED。显示检查数、匹配数与继续加载，详情失败独立提示。建议后端补列表调度状态过滤及计划摘要后移除此兼容查询。
