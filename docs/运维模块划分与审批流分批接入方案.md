# 运维模块划分与审批流分批接入方案

整理日期：2026-10-19

本文按当前讨论整理运维业务模块、审批边界和建议接入顺序，作为分批接入的评审依据，不代表全部功能已经完成。还料是否需要独立审批等待定事项在文中单独标明。

## 一、总体原则

以维修单串起报修、维修记录、报价、人员、物料和各项申请。每一种需要审核的申请独立接入审批流，并关联原维修单，支持分批上线。

- 报修本身不单独增加审批，提交后按值班表分配维修负责人。
- 维修中的报价、内协、物料、转单、关闭、完工申请走审批流。
- 不走审批流的业务也可能需要人员确认，例如客户确认、仓库出库、还料验收。
- 画布负责审批路线和人员规则；业务后端负责权限、状态校验及审批结果落地。
- 每一批都完整打通申请、待办、审批、业务更新和历史记录。

## 二、模块及审批边界

| 模块 | 操作 | 是否走审批流 | 处理逻辑 |
| --- | --- | --- | --- |
| 值班管理 | 排班、调整、保存、导出 | 不走 | 为报修自动分配提供依据 |
| 报修登记 | 填写客户、项目、产品、故障、附件 | 不走 | 提交后生成报修单 |
| 自动分配 | 按值班表确定维修负责人 | 不走 | 无可用值班人员时交主管补派；多人值班时的分配规则需明确 |
| 维修处理 | 开始维修、签到、检查、日志、签退 | 不走 | 负责人和协助人员记录实际工作 |
| 报价申请 | 提交维修报价 | 走 | 运维主管、总经理依次审批 |
| 客户确认 | 记录客户是否同意维修及确认价格 | 不走内部审批 | 内部报价通过后记录客户结果 |
| 内协申请 | 选择协助人员、填写协助内容 | 走 | 运维主管与协助人员所属主管会签，通过后加入维修成员 |
| 维修物料申请 | 选择物料、数量、用途 | 走 | 运维主管审批，通过后待仓库出库 |
| 仓库出库 | 实际发放物料 | 不再走同一审批 | 仓库确认实际数量，产生出库记录 |
| 维修用料 | 记录实际使用及剩余数量 | 不走 | 形成维修单物料记录 |
| 还料 | 提交还料、仓库验收 | 暂按业务确认处理 | 仓库实际收料后才能结清；是否另加审批待定 |
| 转单申请 | 填写原因、备注 | 走 | 运维主管审批并指定新负责人，通过后转交 |
| 关闭申请 | 填写关闭原因、说明、附件 | 走 | 运维主管审批，通过后异常关闭 |
| 完工申请 | 提交维修结果、最终价格等 | 走 | 运维主管审批，通过后正常完成 |
| 客户评价 | 完工后评价 | 不走 | 正常完工后生成评价记录 |
| 查询统计 | 报修列表、维修详情、历史、工时统计 | 不走 | 按角色和参与关系控制可见范围 |

## 三、审批申请拆分

### 1. 关闭审批

- 发起人：维修负责人。
- 填写内容：关闭原因、关闭说明、附件。
- 原因选项：客户弃修、不是问题、其他；选择其他时要求补充说明。
- 审批路线：负责人提交 → 运维主管审批。
- 提交及审批通过时校验打卡已结束、物料已结清。
- 通过后异常关闭；驳回后恢复可处理状态。
- 异常关闭与正常完工区分，不自动进入正常完工评价流程。

当前已保存“维修单关闭审批”设计草稿，标识为 `repair_close`，尚未发布。页面当前仅支持基础控件，因此原因配置为必填文本，说明的条件必填仅有文字提示。单选、条件必填及维修业务绑定仍需补充。

### 2. 转单审批

- 发起人：当前维修负责人。
- 填写内容：转单原因、备注。
- 审批路线：负责人提交 → 运维主管审批并指定新负责人。
- 通过且新负责人有效后，由后端完成负责人变更；审批中或驳回时保持原负责人。
- 保留负责人变更历史、维修日志、报价和物料记录，不重新创建报修单。
- 画布或业务审批页面需要支持审批时选择新负责人。

### 3. 内协审批

- 发起人：维修负责人。
- 填写内容：协助人员、协助内容。
- 审批路线：运维主管与协助人员所属主管会签，不要求固定先后顺序。
- 全部通过后才加入维修成员；审批中不提前授予参与权限。
- 协助人员的主管由后端组织关系解析，不由申请人任意指定。
- 多人跨部门、双方主管相同、主管缺失等情况，需要明确处理规则；不得默认跳过审批。

### 4. 维修物料审批

- 填写内容：物料明细、数量、用途。
- 审批路线：申请人提交 → 运维主管审批。
- 审批通过后进入待出库，仓库实际发放后才形成领料记录。
- 维修用料、剩余物料及还料验收关联同一维修单。
- 已提交还料申请不等于已结清，结清依据实际验收结果。
- 需要物料明细表格及库存业务联动，不能仅用普通文本代替。
- 还料是否增加独立审批尚待确定。

### 5. 报价审批

- 发起人：维修负责人。
- 填写内容：维修报价及相关附件。
- 审批路线：运维主管 → 总经理。
- 驳回后允许修改重提，并保留报价版本及审批历史。
- 内部审批通过后记录客户确认结果及确认价格。
- 审批报价、客户确认价格和最终维修价格应分别保留，便于完工审核追溯。

### 6. 完工审批

- 发起人：维修负责人。
- 填写内容：维修结果、最终价格及相关记录。
- 审批路线：负责人提交 → 运维主管审批。
- 提交及通过前核对工时结束、物料结清、报价与客户确认状态，以及是否存在冲突申请。
- 通过后正常完成并生成评价记录；驳回后继续维修并允许重新申请。

## 四、建议分批接入顺序

| 批次 | 内容 | 主要打通事项 |
| --- | --- | --- |
| 1 | 关闭审批 | 现有草稿、维修单关联、工时与物料校验、审批通过后关闭 |
| 2 | 转单审批 | 审批时指定新负责人、负责人变更及历史保留 |
| 3 | 内协审批 | 动态解析双方主管、会签、通过后加入成员 |
| 4 | 维修物料审批 | 物料明细、主管审核、仓库出库与还料记录 |
| 5 | 报价审批 | 两级审批、报价版本、驳回重提、客户确认 |
| 6 | 完工审批 | 维修结果、价格、工时、物料汇总校验及客户评价 |

以上为建议顺序，可按实际优先级调整。关闭和完工依赖真实工时及物料状态，不能将 Mock 结果或尚未完成的还料申请当作正式结清依据。

## 五、每批接入的完成标准

1. 从原维修详情发起申请，自动关联维修单，不重复填写客户、项目等已有信息。
2. 后端校验发起权限和当前业务状态，保存申请并启动对应审批。
3. 审批人收到待办，能查看维修背景、申请内容及相关附件。
4. 审批通过后由后端更新业务；驳回后提供明确的修改与重提入口。
5. 记录申请人、审批人、意见、时间及每次重提历史。
6. 防止重复提交、重复执行审批结果，并定义并发申请的冲突规则。
7. 验证发起人、审批人和无关人员的权限及数据可见范围。

## 六、当前后端差异与接入边界

根据本次核对的接口文档，当前后端维修业务绑定固定模板 `project_repair_v1`，与本方案仍有差异：

| 项目 | 当前接口描述 | 目标业务 |
| --- | --- | --- |
| 报修分配 | 提交后待主管派单 | 按值班表自动分配，缺少有效值班人员时主管补派 |
| 报价 | 主管审批后线下给客户，不设置客户确认状态 | 运维主管、总经理两级审批，再记录客户确认 |
| 客户弃修 | 提交弃修结果直接结束 | 先发起关闭审批，通过后关闭 |
| 独立申请接入 | 现有固定维修流程承载部分处理步骤 | 逐项接入转单、内协、物料、关闭等独立申请 |

相关现有接口：

- `/repair/order/submit`：提交报修并启动当前固定维修流程。
- `/repair/order/task/submit`：提交当前维修工作节点的数据。
- `/repair/order/workflow/template`：读取固定维修模板。

分批接入前需重新刷新接口文档，逐项确认后端支持情况。不能只修改画布后继续沿用冲突的业务逻辑，也不能让新旧流程同时处理同一项申请。

报修、签到、维修记录等业务页面继续保留。审批配置负责审核路线，业务服务负责真实状态更新；本方案不意味着将所有维修操作都搬进通用表单。
