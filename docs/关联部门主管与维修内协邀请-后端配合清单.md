### 给后端的最小改造顺序

1. **业务目录与能力**：提供“维修内协邀请”场景标识、受邀部门字段的语义及提取路径；返回是否支持关联部门主管规则，避免与其他 `REPAIR_OPS_APPLICATION` 事项混淆。
2. **配置协议**：正式定义通用关联部门主管规则并支持保存、发布、回读。下方 JSON 仅是设计意图示例，字段名/枚举不是已确认接口，不可直接作为现有请求发送。
3. **执行引擎**：校验邀请部门及主管，冻结组织快照。运维主管先审，随后一个关联节点内产生多个部门任务；部门 ALL、同部门 ANY、空主管 FAIL，任何驳回终止剩余任务。
4. **实例回读**：返回关联节点下面的部门组、主管快照、任务标识、任务状态和组通过状态，PC/移动端按部门展示，不只返回平铺审批人。
5. **审批外指定**：全部通过后产生每部门独立待办，并提供候选成员查询、指定提交及状态回读。审批通过接口不要求 `assignedUserIds`；成员加入由独立指定操作触发。
6. **版本与兼容**：新模板仅用于后续申请，旧已发布流程和在途实例不自动迁移；正式协议更新到 Apifox 后再放开前端执行。

```json

    "kind": "DEPARTMENTS",
    "fieldKey": "departments",
    "itemIdPath": "departmentId"
  },
  "departmentMode": "ALL",
  "headMode": "ANY",
  "emptyPolicy": "FAIL"

```

`departments` 和 `departmentId` 为示意；后端需给出实际业务快照的字段路径。通用规则的 `MEMBERS` 来源需另行定义成员部门归属政策，不应默认取首个部门。前端提交业务选择；后端不得信任客户端提供的主管名单，应按组织关系自行解析。同一主管跨部门不能按用户 ID 自动去重。

## 1. 已确定业务规则

- 申请人在维修详情一次选择多个部门，逐部门填写协助原因，不预先选择人员。
- 运维主管先审批；通过后，各受邀部门主管并行审批。
- 部门之间全部通过；同一部门多个主管任意一人办理即可。任一部门驳回，整单退回，不提前加入成员。
- 全部审批结束后，产生各部门独立的“待指定内协人员”业务待办。
- 部门主管在审批之外指定本部门成员；各部门独立指定，指定成功后该批成员加入维修单。指定人员不能作为 review 接口通过审批的必填参数。
- 无主管、部门无效或成员部门不明确时提示异常，不自动通过。

## 2. 第一阶段业务入口

第一步“关联业务”显示“维修内协邀请”。申请内容来自维修业务页面，不是通用自定义表单，不搭建第二套业务表单。配置步骤为：基础信息 → 流程设计 → 更多配置 → 完成发布。

仍需要后端提供只读业务数据目录，供审批展示、条件、关联部门选人使用。“无业务表单配置”不等于没有业务字段。

已知旧业务标识为 `REPAIR_OPS_APPLICATION`，旧模型 key 为 `repair_ops_collaboration`。这个业务类型还包含其他维修事项，不能全局重命名为维修内协邀请。请提供稳定的业务场景/模板标识与绑定方式；前端当前的 `LOCAL_REPAIR_INTERNAL` 仅是本地选项标识，不发送给后端。

## 3. 通用关联部门主管规则

人员配置新增“关联部门主管”，区别于“发起人所属部门负责人”。需要支持两种来源：

1. 业务/表单所选部门：解析单部门或部门集合。
2. 业务/表单所选成员的所属部门：解析成员集合，再按正式组织归属分组。多部门兼职人员的归属规则必须明确，不能随便取第一条。

配置需要表达：来源字段、来源语义、部门之间 ALL/ANY、同部门主管 ANY/ALL、无主管 FAIL。执行引擎不能将部门主管合并成普通 userIds 后使用单层投票。

后端应在提交时校验业务字段并生成主管快照，拒绝客户端提交审批人快照、直接覆盖组织关系。部门去重但不能误合并不同部门任务；同一个主管负责多个受邀部门时，各部门需独立办理或有明确的批量办理协议，不因用户相同自动算全部通过。

字段目录需明确部门、部门集合、成员、成员集合的语义及路径。普通字符串、备注和附件不能成为合法候选。当前前端使用本地 `departments/users` 等类型识别仅供设计；最终请给出标准目录协议，包括列表项字段路径如 departments 中 departmentId 的提取方式。

新增通用规则枚举名称、字段结构、能力标志需后端确认；不要把本规则伪装为 FORM_USERS（后者读取的是用户 ID，不会自动查部门主管）。

## 4. 模板、模型和画布

- 提供业务约束下的新模板：运维主管审批节点 → 关联部门主管节点 → 结束。由后端绑定正确运维主管，不使用发起人直属主管或前端猜测的角色 ID。
- 一个关联节点内部按部门生成任务，主管和通过条件可追溯；不要求前端绘制固定 20 个部门槽位。
- 更新业务目录、设计器能力、保存校验、发布校验、模型回读和执行转换。只支持画布显示但不能执行时，应返回明确阻断原因。
- 维修场景强制全部部门、同部门任一主管以及无主管 FAIL；通用控件可支持其他业务规则，但后端仍需校验场景约束。
- 新版本仅用于后续申请。旧已发布模型、旧 userIds 申请、审批中 assignedUserIds 协议和历史实例保持可追溯，不能前端静默迁移。

## 5. 审批外指定人员

需要提供独立的候选查询、指定提交及状态回读协议（路径尚未确认，前端未臆造接口）。

- 以协助申请及受邀部门定位，检查整单审批已通过、维修单未终止、操作人是该受邀部门可指定主管。
- 候选仅有效本部门成员；服务端校验人员状态、重复成员、跨部门越权及维修单状态。
- 支持幂等或并发版本保护，避免两个主管同时指定造成重复入组；成功后刷新实际成员及权限。
- 状态至少能区分审批中、审批驳回/撤回、审批通过待指定、部分指定、全部指定。部分部门指定成功不应重跑审批。
- 是否允许追加、替换、撤销已指定成员，应提供独立权限及操作协议，不能覆盖已产生的作业历史。
