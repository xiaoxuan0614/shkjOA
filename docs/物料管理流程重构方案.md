# 物料管理全流程重构方案

> 日期：2026-08-12
> 说明：本文档描述物料管理重构后的**完整业务流程**、**需要后端提供的接口**、以及**前端改造计划**。
> 数据字段以 apifox 接口文档为准（`/stock/*`、`/project/customer/*`），文档没有的接口/字段在本方案中明确列出，供后端开发对齐。

---

## 一、业务全景（角色 × 页面）

| 角色 | 页面 | 职责 |
| --- | --- | --- |
| 使用者 | **领料申请** | 按项目申请领料出库，提交后等库管出库 |
| 使用者 | **还料申请** | 按项目申请还料（带出之前未用完的还料列表），提交 |
| 库管 | **采购入库** | 出入库申请(采购类型)流转：新增→确认采购→填快递单号→采购完成→入库 |
| 库管 | **库存管理** | 查看所有在库物料数量，**盘存**调整在库数量 |
| 库管 | **出入库管理** | 查看领料/还料申请，库管**逐条/批量出库、入库、拒绝** |
| 双方 | **物料基本维护** | 物料基础信息维护（编码/名称/类别/品牌/型号/单位/单价/安全库存） |

## 二、流程详述

### 1. 领料申请（使用者）
```
选择关联项目单号 ──自动带出──> 项目名称
（或反向：选项目名称带出单号）
使用人 / 部门 = 当前操作人（默认，不填）
填写：使用时间、备注
物料明细：选物料（展示实时库存）→ 填申请数量 → 选单位（物料维护中配置的单位）
提交 ──> 生成出库申请（待审批）──> 库管在「出入库管理」出库
```
- 若物料无库存或不足：**可正常提交申请，但在备注中标注「待采购」**；等库管采购入库后再申请。
- 库管出库时若库存不足：**拒绝或挂起**（挂起记录原因），不强行出库。

### 2. 还料申请（使用者）
> 说明：还料 = **归还**之前领了没用完的物料，方向为**入库(IN)**；领料为出库(OUT)。
> **三层数量**：应还数量（后端算可还）→ **实际还库数量**（本申请填，默认=应还，不可超）→ **最终入库数**（库管入库时确认，可改）。
```
选择关联项目单号（或项目名）→ 自动带出项目名称/单号
使用人 / 部门 = 当前操作人（默认）
填写：备注
物料明细：根据所选项目，**自动带出该项目之前申请使用中没用完的还料列表**（后端算可还数量）→ 明细列显示 **应还数量** → 填 **实际还库数量**（**不能超过应还数量，前端拦 + 后端兜底**）→ 提交
还料人：记录还料人
提交 ──> 生成还料(入库)申请 ──> 库管确认入库（明细列显示 应还/实际还/最终入，最终入可改，不一致必填说明）
```

### 3. 采购入库（库管，**独立采购订单 /project/purchaseOrder**）
```
① 新增采购订单（/project/purchaseOrder/add）：
   - 供应商（供应商管理 /project/supplier → supplierName）
   - 明细：物料（新物料先新增→同步「物料基本维护」；已维护的直接选）→ 采购数量 → 单价 → 选单位 → 自动算单行总价
   - 整单总价自动合计
   - 提交 → 状态「待采购」
② 确认采购（approve 或状态推进）→ 执行状态「采购中」
③ 采购完成 → 执行状态「已到货」
④ 入库（**逐条或批量**）：
   - 明细列：采购数量/采购单价 + **实际入库数量**（默认=采购数，可改）+ **实际单价**（可改）+ **规格型号**（可改）+ **差异说明**（实际≠采购 或 型号变化时**必填**）
   - 差异逐条写入台账 `remark` 留痕（如「规格由A改为B，实际入库3」）
   - 生成**入库台账**（manualIn）→ 执行状态「已入库」
```

### 4. 库存管理（库管）
- 展示所有在库物料：编码/名称/类别/基准单位/库存数量/安全库存/库存金额
- **盘存**：调整某物料在库数量。**留痕**（记录盘点前数量/盘点后数量/差异/操作人/时间），**暂不做审核**（后续加审核流程）

### 5. 出入库管理（库管）—— **明细维度出库/入库**
- 展示**领料/还料/采购申请记录**（含状态）+ 明细查看。
- **逐条/部分出库·入库（核心）**：点某申请「出库/入库」→ 打开**出入库执行弹窗**：
  - 明细表每行：勾选 + 物料/规格 + 单位 + 申请数量 + **本次执行数量**（默认=申请数量，可改）+ **说明**（差异留痕，选填）
  - **可只勾部分明细** → 支持「部分出库」（一张单的部分物料出库；如申请 5 实际只出 3）
  - 已执行完的明细行置灰不可选（防重复）；**剩余可执行数 = 申请数量 − 已执行数量**（前端聚合台账 `sourceId+materialId`，或后端 queryById 返回）
  - 点「执行出库/入库」→ 整单一次 `POST /stock/apply/execute`（`items:[{itemId, executeQty=本次执行数}]`，方向由申请决定，执行人后端从 token 取）→ 后端写台账；说明留痕待后端补 `remark` 字段后随 execute 提交
- **还料入库三层数量**（明细列全展示）：**应还数量**（后端算）→ **实际还库数量**（还料申请时填）→ **最终入库数**（库管入库时改，默认=实际还库数量）；三者不一致 → **逐条必填说明**
- **采购入库差异**：实际入库数量/单价/**规格型号**与采购单不一致时可改，差异**必填说明**（如「规格由A改为B」），逐条写台账 remark 留痕
- **批量出库/入库**：列表勾选多张申请 → 每张申请一次 `executeApply`（已通过明细按「剩余可执行数=申请−已执行」作为 `executeQty`，跳过已执行完明细；批量不逐条改，差异留给单条弹窗）
- 其余保留：**审批**(通过/驳回) / **挂起**(填原因) / **拒绝**(填原因) / 申请人**撤回·删除·修改**
- 出库/入库后更新库存并写入台账

### 6. 物料基本维护（双方）
- 物料基础信息 CRUD：编码(自动生成)/名称/类别/品牌/型号/基准单位/基准单价/安全库存/备注
- **单位子表**：每个物料配置多个单位（第一个为基准单位），供领料/采购时选择单位
- 新物料在采购入库里新增时，信息同步到这里

## 三、数据模型与接口对照

### 3.1 现有接口（apifox 文档已有，直接使用）
> 说明：**领料 / 还料 / 采购 三个业务统一用「出入库申请」`/stock/apply/*` 接口建模**，用 `applyType`（领料=OUT 出库，还料/采购=IN 入库）+ `bizType`（PICK/RETURN/PURCHASE）区分，不再单独开发采购单接口。

| 接口 | 用途 |
| --- | --- |
| `GET /stock/material/list` | 物料列表（含库存/单位子表 unitList） |
| `GET /stock/material/queryById` | 物料详情 |
| `POST /stock/material/add` / `edit` | 新增/编辑物料 |
| `DELETE /stock/material/delete` / `deleteBatch` | 删除物料 |
| `GET /stock/ioRecord/list` | 出入库台账 |
| `POST /stock/ioRecord/manualIn` / `manualOut` | 手动入库/出库 |
| `GET /stock/apply/list` / `queryById` | 出入库申请列表/详情（领料/还料/采购都在这） |
| `POST /stock/apply/add` / `edit` | 新增/编辑出入库申请（领料/还料/采购提交） |
| `DELETE /stock/apply/delete` / `deleteBatch` | 删除申请 |
| `POST /stock/apply/approve` / `reject` / `cancel` | 审批通过/驳回/取消（采购状态流转、库管审批） |
| `POST /stock/apply/execute` | 申请-执行出入库（单条/批量统一；`applyId + itemIds + items:[{itemId, executeQty}]`，方向由申请决定） |
| `GET /project/customer/list` 等 | 客户管理（用作**供应商**选择） |

### 3.2 需要后端提供/扩展的接口（文档没有）

| # | 接口 | 说明 |
| --- | --- | --- |
| 1 | **项目接口** `/project/*` | 领料/还料选项目单号自动带出项目名称（或反向）。目前 `/project/*` 后端未实现 |
| 2 | **还料列表接口** | 按项目单号带出该项目之前「未用完/可还料」的物料列表（后端算可还数量） |
| 3 | **盘存接口** | 调整某物料在库数量（盘存），**留痕**：记录盘点前/后数量/差异/操作人；暂不做审核（后续加） |
| 4 | **批量出入库接口** | ✅ 已用 `/stock/apply/execute` 实现（单条/批量统一：前端按申请逐张调 execute，已通过明细按剩余可执行数作为 `executeQty`） |

> **采购**不单独开发接口：采购 = 出入库申请（`/stock/apply/add`，`applyType=IN`、`bizType=PURCHASE`），通过扩展字段（供应商/快递单号）+ 状态流转（approve 或 status）实现。

| 实体 | 需扩展字段 | 用途 |

## 六、业务规则确认（已和业务确认）

| 问题 | 确认结论 |
| --- | --- |
| 还料语义/方向 | 还料 = 归还之前领了没用完的物料，方向 **IN 入库**；领料 = 出库 OUT |
| 还料"没用完"数量 | 后端算（领料数量 − 已用），前端展示 + 改数量 |
| 还料数量校验 | **前端拦 + 后端兜底**（不能超可还数量） |
| 采购入库 | **逐条或批量入库**，入库生成台账；入库前**可修改入库信息**（实际入库可能与采购单不一致，需备注说明） |
| 盘存 | **留痕**（盘点前/后数量/差异/操作人）；**暂不审核**（后续加审核） |
| 库存不足的领料 | **可申请但备注标注「待采购」**；库管出库时库存不足则**拒绝或挂起**（挂起记录原因） |
| 挂起落库方式 | apifox 无挂起接口 → **走 `/stock/apply/reject`**，`approvalComment` 前缀「挂起：原因」，前端按前缀展示「已挂起」（2026-08-13 确认） |
| 部分出库/入库 | **明细维度**执行：可只勾部分明细、可改本次执行数量（默认=申请数量）；已执行明细防重复 |
| 还料三层数量 | **应还数量**（后端算）→ **实际还库数量**（还料申请填）→ **最终入库数**（库管入库改，默认=实际还库）；不一致**逐条必填说明**留痕 |
| 采购入库差异 | 实际入库数量/单价/**规格型号**可改，差异**必填说明**，逐条写台账 `remark` 留痕 |
| 差异留痕 | 统一写入台账 `remark`（如「库存不足少出2」「规格由A改为B」）；剩余可执行数 = 申请数量 − 已执行数量 |

## 七、依赖后端（开发项）

1. **项目接口** `/project/*`（项目单号↔项目名）—— 领料/还料项目联动（若暂不实现，前端先用项目字典下拉）
2. **还料列表接口** —— 按项目带出未用完可还料列表
3. **盘存接口** —— 调整在库数量（留痕）
4. **StockApply 扩展字段**（`bizType` PICK/RETURN/PURCHASE、`projectNo/projectName`、`returnUser`、`supplierName`、`expressNo`、`executeStatus`）
5. **批量出入库接口** —— ✅ 已用 `/stock/apply/execute` 实现（单条/批量统一，前端按申请逐张调 execute）
6. **明细已执行数量**：`StockApplyItem` 扩展 `outQty`(领料已出库) / `inQty`(还料/采购已入库)，或 queryById 返回"剩余可出/可入数"（防重复 + 算剩余）
7. **还料应还数量快照**：`StockApplyItem` 扩展 `shouldReturn`（还料申请提交时把 canReturn 存下来，供入库弹窗显示三层数量）

> **采购不单独开发接口**：复用「出入库申请」`/stock/apply/*`（applyType=IN、bizType=PURCHASE）+ 扩展字段（供应商/快递单号/执行状态）实现。
> 前端会先按文档已有字段对齐实现；缺接口/字段的页面（领料/还料/采购/盘存）先搭骨架 + 按约定字段对接，后端就绪即插即用。
